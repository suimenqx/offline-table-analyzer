# 提取目标的场景与边界：决策材料

本材料用于回答“用户希望从粘贴内容得到什么”，不是新架构或验收标准的最终决定。用户已将讨论重点从格式识别转向信息提取，并接受先评估表、字段和多表关系的目标范围。以下项目事实来自现有需求及内置样例；边界样本是为了暴露歧义而设计的假设场景，需要真实数据验证。

## 已有产品证据

- `docs/planning/refactor-requirements.md` §2 把工程师检查诊断日志、命令行表、网页表和 Excel 复制内容，以及分析人员 JOIN 多表，列为主要工作。
- `src/ui/app.js` 的内置样例一次输入三张 `table-data` 表：`Inventory`、`Orders`、`SystemLogs`。这支持“同一来源包含多张表”是现有核心场景。
- `docs/planning/requirements.md` §1–2 明确用户需要可检查、可筛选、可 JOIN、可导出的表，并要求歧义与数据丢失可见。现有输入覆盖文字、HTML 剪贴板和本地文件。
- 这些材料只能证明目前产品支持什么，不能证明未来用户希望从任意文本中抽取实体、摘要或任意知识图谱。

## 需要明确的边界样本

| 样本 | 候选有用结果 | 隐含歧义及失败方式 |
| --- | --- | --- |
| `导出时间：10:00` 后接 `ID,金额` 两行表，再接 `合计仅供参考` | 一张数据表；标题、说明、合计和未提取片段保有原文依据 | 把说明吞作数据行会造假；完全不显示说明可能丢失重要限定条件。 |
| `table-data Inventory` 与 `table-data Orders` 连在一次粘贴中 | 两张表，各自字段和记录；可提出基于 `ProdID`/`ID` 的关联候选 | 强行合并会丢失表边界；仅因列名相似就自动 JOIN 会制造错配。 |
| `request_id=R7 status=500 duration=30ms` 只有一行 | 一条键值记录或“证据不足”的预览，由目标范围决定 | 一行不能证明重复字段语法、数据类型或未来规则可泛化。 |
| 连续三行 `10:01 WARN disk=90%` 等日志 | 若目标包含重复记录，可提取时间、级别、消息/键值 | `WARN` 是字段值还是消息前缀、空格和等号的意义都可能不唯一。 |
| `Name Age` 加 `Alice 30` | 可预览两列一行，也可能需用户确认表头 | 只有两行时，自动结构归纳缺少足够证据断言第一行一定是表头。 |
| `UserID` 出现在两张表 | 两张独立表，附待确认的关系候选 | 同名列可能只是编码空间碰巧一致；在确认前自动 JOIN 会放大错误。 |

## 三个产品范围选择

1. **表优先，保留上下文。** 自动提取所有有记录结构的表及字段；标题、说明、疑似遗漏仍与原文关联。单条键值和日志的纳入有明确门槛。多表关系先作为候选。这与当前分析工作台最接近，但需要定义“表”的下限。
2. **整份文档结构化。** 表、标题、段落、实体、键值与关系都是一等结果。覆盖范围大，但输出模型、校验、UI 和评估语料都会显著扩大；“可分析表格”可能不再是主任务。
3. **目标字段优先。** 用户先指定想要的字段或示例，系统只提取相关记录。能直接表达意图，但初次粘贴的零配置体验较弱，且未选内容仍需安全保留。

初步建议为第一项，并让用户可在草稿上点选遗漏字段或记录；这只是待确认方向。无论哪项，都需要把“本次输入提取正确”与“推断规则可复用到未来输入”分开声称。[FlashExtract](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/12/pldi14-flashextract.pdf) 支持由示例表达意图；[Datamaran](https://arxiv.org/pdf/1708.08905) 说明无预置格式的归纳仍需重复证据与偏好，二者都不能单独保证短样本的唯一解释。
