# ADR: 卡片式数据源工作区与 Worker 多数据集会话

状态：已决策，2026-10-18，待实施。来源：[Wayfinder 地图 #13](https://github.com/suimenqx/offline-table-analyzer/issues/13)，票「卡片/表池/view 领域模型与迁移」「卡片的产品交互设计」「卡片工作区原型」「Worker 多数据集架构决策」的决议汇总。本文记录架构决定；交互决议与术语见对应票与 GLOSSARY。

## 决定

1. **工作区层级**：工程 = 页签容器；卡片 = 数据段（一份原文 + 独立解析策略 + 显隐）；表池 = 所有可见卡片解析出的表集合；view = 命名保存的表组合（表集合 + JOIN 配置），与卡片解耦。术语已落 GLOSSARY。
2. **表池语义**：与首张卡结构（列名+列顺序）一致的同名表直接拼接（**不去重**，重复保留）；结构不同的同名表并列显示（冲突时加卡片名限定）；拼接顺序 = 卡片列表顺序。
3. **Worker 共享会话**：计算 Worker 持有 `Map<cardId, 数据集>`；表池在 Worker 内派生；Window 每次查询只传**可见清单**（卡片 id + 顺序），不传表数据。拼接、JOIN、导出均在 Worker 内，零跨线程复制。依据：[多卡片表池的内存与 Worker 事实调研](../planning/multi-card-worker-memory-research.md)——postMessage 数据复制非共享、字符串无零拷贝，多数据集同驻才互见。
4. **解析与驻留生命周期**：解析发生在**选中卡片**，结果驻留共享会话；**显隐不触发解析也不释放**（显隐只改表池成员）；**删除卡片才释放**其数据集。
5. **修正按来源应用**：单来源池内表应用其卡片自己的 `cellEdits`（键仍 `$表名`）；拼接表**只读、不应用修正**（多来源无追溯机制）。
6. **预算与超限**：单卡解析沿用 800 万单元格上限；会话总预算（全部驻留数据集合计）初值同 800 万，CI 校准后再调；超限**明确报错、不静默截断、原文保留**。
7. **取消与恢复**：解析/查询走**作业级取消**（不杀其他卡的数据）；Worker 崩溃/终止 = 共享会话整体丢失，**按需惰性重建**（哪张卡需要就重解析哪张；原文在 Store 是唯一权威），失败可见。
8. **边界不变**：BackgroundService 保持唯一 Worker 生命周期/版本握手/消息传输拥有者，会话状态从单 `datasetKey` 升级为多卡；显隐真相在 Store（UI 经 dispatch 写），Worker 只读清单派生；查询缓存失效键含可见清单修订与各卡修订；不引入多 Worker 协调层、不外存查询、不改变单 HTML/零运行时依赖/离线交付模型。

## 依据与权衡

- **共享会话 vs 每卡一个 Worker**：每卡 Worker 独立堆、可独立终止，但总驻留内存更高、需要新的多 Worker 协调层、且违背「BackgroundService 唯一拥有者」的既有支柱；共享会话下多数据集互见、拼接与跨卡查询零复制，代价是单 Worker 内存增长直接占用预算、崩溃损失面更大——以预算上限（第 6 条）与惰性重建（第 7 条）对冲。
- **显隐不释放数据集**：若隐藏即释放，显隐抖动退化为反复全量解析（10 万行 × 32 字段解析秒级），违背「显隐 = 纯范围控制」的卡片职责；内存回收由删除卡片承担。
- **拼接只读**：多来源拼接后行归属无法确定，单元格修正的键与失效语义无从落点；保持只读是最小诚实语义，单一来源时行为与 23.x 完全一致。

## 实施影响面

- `WorkerRuntime`：会话从单 `rawTables` + `key` 改为多数据集 Map；`assertCurrent` 按卡校验；`applyEdits` 按来源卡应用。
- `BackgroundService`：`datasetKey` → 多卡会话状态；`prepare` 按卡惰性解析。
- `QueryService`：表池派生入口（可见清单 → 池）、缓存键含显隐修订；JOIN/导出作用于池。
- `Store`/schema：21→22，`docs` → `projects`/`cards` 1:1 保 id；`activeId` → 工程+卡片两级；`globalViews` 复用，`enabledViews` 合并上移工程级；迁移、备份导入同路径、旧 fixture 回归。
- `refactor.md` 模块边界随实施更新；架构校验继续拒绝越过 Store 的 UI 写入与不完整 manifest。

## 空状态与删除（2026-10-19 修订）

- 工程与卡片均可删至零。删除最后一张卡片保留工程和工程级 view；删除最后一个工程后，工作区为空，自动工程编号归 1。
- `curr()` / `getDocument()` 无当前卡片时返回 `null`；只读访问、渲染、重启恢复和复制空工程均不得补建内容。仅首次无存档启动保留默认工程/卡片；空状态通过明确的新增按钮退出。
- UI 清除已删除来源的原文预览、解析结果、选择与编辑历史，禁用依赖卡片的输入/解析/导出；删除事件携带活动卡片变化及被移除的卡片 id，App 据此同步编辑器并释放 Worker 数据集。
- 空工程和空工作区使用既有 schema 22 的空数组/null 表达，备份保存工程容器并允许恢复零卡片；schema 21 的空备份仍经现有迁移路径处理。无新的持久化字段、运行时依赖或模块。
- 理由：此前「删除后读状态时惰性补建」使用户无法真正清空，并在不可见处占用编号；显式空状态比伪删除后自动重建更符合删除语义。

## 兼容性附注

- 单卡工程重命名时同步其唯一卡片的标题：保留 v22 前「页签重命名 → 原文导出文件名随之变化」的公开行为（导出前缀取卡片标题）；多卡工程只改工程名。
- `tab:*` 命令保留为 `project:*` 的别名、旧形状工作区状态（docs/activeId 无 projects）由 `ensureProjects` 按 1:1 惰性归一化——均为迁移兼容路径，不构成新能力。
